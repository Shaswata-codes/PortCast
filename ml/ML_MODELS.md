# PortCast ML Models, Features, Optimizations, and Evaluation

## 1. Purpose

PortCast predicts dry-bulk freight rates and exposes uncertainty bands for operational decisions such as charter timing, route analysis, and cargo-cost estimation.

The ML pipeline supports:

- A point freight-rate forecast in `$ / MT`.
- A lower P10 quantile bound.
- An upper P90 quantile bound.
- A recursive 30-day trajectory.
- 7-day, 14-day, and 30-day forecast horizons through the FastAPI service.
- Model metadata and feature importance for the explainability UI.

The implementation is distributed across:

| File | Responsibility |
|---|---|
| `train.py` | Dataset loading, feature selection, training, tuning, stacking, metrics, and model persistence. |
| `stacking.py` | Runtime wrapper for the persisted P90 LightGBM/XGBoost stack. |
| `service.py` | FastAPI loading, recursive inference, point ensemble serving, P10/P90 response generation, and radar integration. |
| `testmodel.py` | Accuracy gates, feature checks, and FastAPI contract tests. |
| `data_builder.py` | Composite dataset creation and feature engineering inputs. |
| `models/freight_forecasting_bundle.pkl` | Serialized trained models and metadata used by the API. |
| `models/model_metadata.json` | JSON metrics and top-feature summary used by the Node.js/UI layers. |

## 2. Current Model Architecture

### 2.1 Point forecast: LightGBM plus XGBoost

The point forecast has two independently trained tree-gradient-boosting models:

```text
LightGBM point prediction
             +
XGBoost point prediction
             ------------------
                    2
             = served point forecast
```

The runtime formula is:

```text
point_forecast = (lightgbm_prediction + xgboost_prediction) / 2
```

#### LightGBM point model

Class: `lightgbm.LGBMRegressor`

Current configuration selected by the compact tuning search:

```python
{
    "n_estimators": 160,
    "learning_rate": 0.05,
    "num_leaves": 23,
    "random_state": 42,
    "verbosity": -1,
}
```

Purpose:

- Main point-rate learner.
- Captures nonlinear relationships between freight rates, market indicators, congestion, seasonality, and causal rate history.
- Provides feature importance values.

#### XGBoost point model

Class: `xgboost.XGBRegressor`

Current configuration:

```python
{
    "n_estimators": 300,
    "learning_rate": 0.03,
    "max_depth": 6,
    "subsample": 0.85,
    "colsample_bytree": 0.85,
    "random_state": 42,
    "tree_method": "hist",
}
```

Purpose:

- Independent point forecast with a different tree implementation and inductive bias.
- Provides model diversity for the point ensemble.
- Acts as a base learner in the P90 stack.
- Its feature importances are combined with LightGBM importances for the UI.

XGBoost is therefore doing real work. It is not currently served as a standalone prediction, but its prediction changes the point ensemble and its P90 quantile prediction contributes to the P90 stack.

### 2.2 P10 lower quantile model

Class: `lightgbm.LGBMRegressor`

Configuration:

```python
{
    "objective": "quantile",
    "alpha": 0.10,
    "n_estimators": 180,
    "learning_rate": 0.04,
    "num_leaves": 23,
    "random_state": 42,
    "verbosity": -1,
}
```

Purpose:

- Estimates a lower freight-rate boundary.
- Represents a relatively favorable or low-rate outcome.
- Is used as the lower side of the uncertainty interval.

### 2.3 P90 upper quantile stacking model

The P90 model is a leakage-safe stack with three stages:

```text
Training features
       |
       +--> LightGBM quantile base model, alpha=0.90
       |
       +--> XGBoost quantile base model, alpha=0.90
                       |
             walk-forward out-of-fold predictions
                       |
             LightGBM quantile meta-model, alpha=0.90
                       |
                 P90 stack prediction
```

Base model settings:

- LightGBM: `objective="quantile"`, `alpha=0.90`, 180 estimators, learning rate `0.04`, `num_leaves=23`.
- XGBoost: `objective="reg:quantileerror"`, `quantile_alpha=0.90`, 180 estimators, learning rate `0.04`, `max_depth=4`, `min_child_weight=3`, subsampling `0.85`, and column subsampling `0.85`.
- Meta-model: LightGBM quantile regression with `alpha=0.90`, 100 estimators, learning rate `0.04`, and `num_leaves=7`.

To prevent target leakage, the meta-model is trained from base-model predictions generated by `TimeSeriesSplit(n_splits=3)`. Base models are trained on earlier rows and predict later validation rows. The base models are then refit on the complete training partition for final inference.

The `P90StackingModel` wrapper stores the two base models and the meta-model and exposes a standard `.predict(X)` method for the API.

The wrapper also applies an interval-ordering guard:

```text
P90 = max(P90_stack, P10)
```

This guarantees that the upper bound cannot fall below the lower bound.

## 3. Training Data and Features

The processed dataset is `data/processed_freight_master.csv`. The latest trained dataset contains approximately 4,257 rows and 40 columns, including the target and engineered fields.

The target is:

- `target_rate`: freight rate used as the supervised learning label.

The model uses 39 feature columns. Six of them are created inside `train.py` from historical target values and are not stored as raw CSV columns.

### 3.1 Market and commodity features

- `comm_aluminum`
- `comm_brent_crude`
- `comm_copper`
- `comm_gold`
- `fuel_price_usd`
- `freight_rate_usd`
- `cl=f_close`
- `sblk_close`
- `gnk_close`

These provide commodity, energy, freight-market, and shipping-equity signals.

### 3.2 Port, disruption, and service features

- `avg_wait_days`
- `disruption_index`
- `backlog_teu`
- `on_time_pct`
- `wait_days_ma_7`
- `wait_days_ma_14`
- `wait_days_ma_30`

These represent congestion, disruption severity, backlog, schedule reliability, and smoothed waiting time.

### 3.3 Calendar and seasonal features

- `month`
- `quarter`
- `day_of_year`
- `is_sw_monsoon`
- `is_cyclone_season`

These allow the model to learn annual and monsoon-related behavior.

### 3.4 Rate history features

The following causal lag features are created from `target_rate`:

- `rate_lag_1`
- `rate_lag_2`
- `rate_lag_3`
- `rate_lag_5`
- `rate_lag_7`
- `rate_lag_14`

These are available only from prior observations, so they do not use the current target value.

### 3.5 Rolling statistics and momentum

- `rate_ma_7`, `rate_ma_14`, `rate_ma_30`
- `rate_std_7`, `rate_std_14`, `rate_std_30`
- `rate_momentum_7`, `rate_momentum_14`, `rate_momentum_30`
- `oil_ma_7`, `oil_ma_14`, `oil_ma_30`

Moving averages reduce day-to-day noise, standard deviations represent volatility, momentum captures recent direction, and oil averages represent smoothed energy pressure.

### 3.6 Leakage prevention

The contemporaneous `bdry_close` field is excluded from training because it is on the same time scale as the target and could make evaluation unrealistically optimistic. The future target fields are also excluded:

- `target_lead_7d`
- `target_lead_14d`
- `target_lead_30d`

Rows with missing target values are removed. Features are forward-filled and remaining missing feature values are filled with zero. The first rows that lack causal lag history are removed by the evaluation helper and are filled according to the training preparation flow where appropriate.

## 4. Training and Optimization Strategy

### 4.1 Chronological holdout

The data is split without shuffling:

```text
First 85%  -> training partition
Final 15%  -> untouched chronological holdout
```

This is appropriate for a time-dependent rate series because future observations do not influence training.

### 4.2 Compact LightGBM tuning

`_tune_lightgbm()` evaluates three small candidate configurations on an ordered validation slice inside the training partition:

```python
[
    {"n_estimators": 180, "learning_rate": 0.04, "num_leaves": 15},
    {"n_estimators": 240, "learning_rate": 0.03, "num_leaves": 31},
    {"n_estimators": 160, "learning_rate": 0.05, "num_leaves": 23},
]
```

The candidate with the lowest validation MAE is selected. This keeps training time low while still adapting model complexity to the current dataset.

The latest run selected:

```text
n_estimators = 160
learning_rate = 0.05
num_leaves = 23
validation MAE = 1.6021
```

### 4.3 Reduced model complexity

The current optimization reduces training cost through:

- A small LightGBM parameter search rather than a large grid search.
- Histogram-based XGBoost training with `tree_method="hist"`.
- Moderate estimator counts for quantile base models.
- A shallow P90 meta-model with `num_leaves=7`.
- A restricted XGBoost P90 depth of `4`.
- A 3-fold chronological stack instead of a large cross-validation sweep.
- Feature exclusion for contemporaneous and future target fields.

The raw number of time-series rows is retained. Reducing rows would discard historical information and is not the preferred optimization for this dataset.

### 4.4 Feature importance

LightGBM and XGBoost feature importances are normalized independently and averaged when XGBoost is available. The top 10 features are saved to `model_metadata.json` for the SHAP-lite/explainability UI.

## 5. Runtime Serving Flow

The FastAPI service loads `models/freight_forecasting_bundle.pkl` during application lifespan startup and loads the latest target-rate history for recursive inference.

For each trajectory day, the service:

1. Starts with the latest target-rate history.
2. Rebuilds lag, rolling, volatility, momentum, calendar, and seasonal features.
3. Calls the LightGBM/XGBoost point ensemble.
4. Appends the predicted point rate to the recursive history.
5. Calls the P10 LightGBM model.
6. Calls the P90 stacking wrapper.
7. Returns the point forecast and uncertainty bounds.

The `/api/ml/forecast` endpoint then:

- Generates a 30-day trajectory.
- Produces 7-day, 14-day, and 30-day horizon summaries.
- Applies the live geopolitical risk multiplier.
- Re-anchors the relative trajectory to the requested current/base rate.
- Returns P10 and P90 values for UI charts and booking-window recommendations.

The `/api/ml/health` endpoint exposes the persisted metrics and whether the model bundle loaded successfully.

## 6. Accuracy and Evaluation Metrics

### 6.1 Point-model metrics

The latest chronological 15% holdout results recorded in `model_metadata.json` are:

| Model | RMSE | MAE | R2 |
|---|---:|---:|---:|
| LightGBM point | 0.1901 | 0.1422 | 0.9950 |
| XGBoost point | 0.2049 | 0.1516 | 0.9941 |
| LightGBM + XGBoost average | 0.1850 | 0.1364 | 0.9952 |

The ensemble improves on both individual point models for this holdout. This confirms that XGBoost contributes useful diversity even though its standalone score is slightly weaker than LightGBM.

### 6.2 P90 metrics

P90 is evaluated with quantile pinball loss, where lower is better. The latest recorded values are:

| P90 predictor | Pinball loss | MAE |
|---|---:|---:|
| LightGBM base | 2.1289 | Not recorded separately |
| XGBoost base | 2.1119 | 21.1193 |
| P90 stack | 2.1103 | 21.1029 |

The stack improves P90 pinball loss over both the LightGBM and XGBoost base predictions in the recorded holdout.

### 6.3 Interval metrics

The evaluation checks:

- **Coverage:** proportion of actual values inside `[P10, P90]`.
- **Quantile crossings:** number of rows where `P10 > P90`.
- **Pinball loss:** quantile-specific prediction quality.

Latest direct chronological check:

```text
P10-P90 coverage:       71.27%
Quantile crossings:     0
```

The pytest gate allows coverage between `60%` and `95%`. The current 71.27% result passes this gate and indicates a useful, non-degenerate interval rather than an interval that contains every value.

### 6.4 Important evaluation note

There are two evaluation paths:

1. The training metadata and direct report use the chronological 85%/15% split.
2. The `_backtest()` helper in `testmodel.py` currently uses a seeded random 20% sample for its pytest accuracy gates.

The chronological holdout is the more representative estimate for future forecasting. The random pytest checks are useful regression gates, but they should not be presented as the primary production accuracy estimate.

## 8. Retraining and Model Artifacts

Retrain after changing the dataset, feature engineering, or model settings:

```powershell
cd ml
.\venv\Scripts\python.exe train.py
```

Generated artifacts:

- `models/freight_forecasting_bundle.pkl`: serialized LightGBM, XGBoost, quantile, stack, feature, and metric objects.

## 10. Current Limitations and Future Improvements

- The P90 stack uses two base model families; adding another genuinely diverse model should be justified by out-of-sample improvement and training cost.
- The P10 model is currently tuned less extensively than the point model.
- The pytest backtest should eventually use the same chronological protocol as the primary report.
- Multiple rolling-origin evaluation windows would provide a more stable estimate than one final holdout.
- Early stopping could reduce training time further if validation sets and compatible callbacks are added consistently.
- P90 coverage should be monitored after deployment because market regimes and disruption patterns can change.
- The recorded P90 MAE is large relative to point-rate MAE because it measures upper-quantile predictions against actual values, not central point predictions; pinball loss and interval coverage are the primary P90 measures.
